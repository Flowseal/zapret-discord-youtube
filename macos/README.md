# zapret-discord-youtube на macOS

Порт этой сборки на macOS. Есть два движка, оба собираются из исходников
[bol-van/zapret](https://github.com/bol-van/zapret) командой `./macos/zapret.sh build`:

| | **macws** | **tpws** |
|---|---|---|
| что это | движок `winws`/`nfqws` + бэкенд пакетов для macOS (в этом репозитории) | прозрачный прокси из zapret, как есть |
| уровень | пакеты (IP/TCP/UDP) | TCP-поток |
| стратегии | **те же `.bat` файлы, что в Windows** (все 22) | `macos/strategies.conf` |
| fake, seqovl, multidisorder, fakedsplit | да | нет |
| QUIC/HTTP3 (udp/443) | фейки QUIC, как в Windows | глушится, браузер уходит на TCP |
| голос Discord (udp 19294-19344, 50000-50100), STUN | да | нет |
| UDP-игры (`Game Filter`) | да | нет |
| split/disorder/oob/tlsrec | да | да |
| IPv4 / IPv6 | IPv4 + IPv6 (v6 — если есть маршрут, проверяется `selftest`) | IPv4 + IPv6 |
| root | обязателен | нужен для прозрачного режима, режим SOCKS — без root |

`.bat` файлы и `winws.exe` напрямую на macOS не работают: в них зашит WinDivert.
`macws` берёт из `.bat` аргументы стратегии и порты фильтра и запускает ту же
логику обхода нативно.

## Меню (без команд)

Аналог `service.bat`: **двойной щелчок по [`macos/service.command`](./service.command)**
в Finder — macOS откроет его в Терминале с меню:

```
══════════ zapret для macOS ══════════
 движок:      macws (auto)
 стратегия:   general.bat
 обход:       не запущен
 автозапуск:  нет
 game filter: off
──────────────────────────────────────
  1. Включить обход          6. Выбрать стратегию          11. Обновить ipset-all.txt
  2. Остановить              7. Подобрать стратегию        12. Собрать / обновить движки
  3. Перезапустить           8. Проверить бэкенд macws     13. Диагностика и правила pf
  4. В автозапуск            9. Переключить движок          0. Выход
  5. Убрать автозапуск      10. Game Filter
```

Пароль администратора спрашивается только для пунктов, которым он нужен. Выбор
стратегии, движка и Game Filter сохраняются в `macos/config`. То же меню из
терминала: `./macos/zapret.sh menu`.

## Быстрый старт (командами)

```sh
# 1. собрать движки (нужны Command Line Tools: xcode-select --install)
./macos/zapret.sh build

# 2. проверить бэкенд macws (создаёт utun, шлёт тестовый пакет, всё убирает за собой)
sudo ./macos/zapret.sh selftest

# 3. подобрать стратегию, перебирая .bat как в service.bat -> Run Tests
sudo ./macos/zapret.sh test-bat

# 4. включить и поставить в автозапуск
sudo ./macos/zapret.sh start "general (ALT4).bat"
sudo ./macos/zapret.sh install "general (ALT4).bat"
```

Если `selftest` не прошёл — движком остаётся `tpws` (`ENGINE=auto` это учитывает),
подбор стратегии тогда: `./macos/zapret.sh test` (без sudo).

Перед проверкой **включите DoH/Secure DNS** (п.1 основного README): часть
блокировок делается подменой DNS, обход DPI от неё не спасает.

| `list` | стратегии: `.bat` для macws и список из `strategies.conf` для tpws |

| `socks [стратегия]` | tpws как SOCKS5 на `127.0.0.1:1080`, без sudo |
| `check [стратегия]` | печатает будущие правила pf, проверяет их `pfctl -n` и параметры движка, ничего не применяя (sudo) |

| `tune [хост]` | перебирает 46 наборов параметров desync по одной цели и показывает, какой пробивает большой ClientHello (sudo) |

| `stop` / `restart` / `status` | остановить / перезапустить / показать состояние |

| `update-ipset` | обновить свою копию списка адресов в `macos/.state` (подключается при `IPSET_FILTER=loaded`) |

Имя стратегии для macws можно писать коротко: `ALT4`, `EXP`, `FAKE TLS AUTO ALT2`
— скрипт найдёт соответствующий `general (...).bat`.

## Как работает macws

В macOS нет ни NFQUEUE, ни divert-сокетов (ipfw удалён, в pf нет `divert-packet`),
поэтому штатные `nfqws`/`dvtws` там бесполезны. Бэкенд
([`macos/src/mac_backend.c`](./src/mac_backend.c)) делает так:

1. Создаёт интерфейс `utun` (kern_control, как у VPN-клиентов).
2. Пишет в anchor `zapret` правила pf вида
   `pass out route-to (utunN 10.77.77.2) inet proto tcp from any to !<nozapret> port {80,443,...} user { >root }`.
   Порты берутся из `--wf-tcp`/`--wf-udp` выбранного `.bat`, локальные сети
   исключаются по `lists/ipset-exclude.txt`.
3. Исходящие пакеты приходят в userspace, их обрабатывает **неизменённая** логика
   nfqws (`processPacketData`): фейки, split/seqovl, hostlist, ipset — всё как в Windows.
4. Результат отправляется заново кадром через **BPF** прямо в интерфейс выхода,
   минуя стек ядра (в macOS 26 raw-сокет с `IP_HDRINCL` на отправку отвечает
   `No route to host`, поэтому BPF — способ по умолчанию; `MACWS_INJECT=raw`
   переключает обратно). Так наши пакеты вообще не проходят через pf, и заворота
   по кругу быть не может.
5. Входящий трафик не трогается вообще — идёт штатным путём ядра.

> [!IMPORTANT]
> Тонкость, из-за которой обход молча не работал: nfqws оставляет контрольную
> сумму IP-заголовка своих пакетов нулевой, потому что при отправке через
> raw-сокет её считает ядро. При записи кадра через BPF ядро не участвует,
> поэтому сумму считает бэкенд — иначе пакеты отбрасывает первый маршрутизатор,
> и это выглядит как «стратегия не помогает» (фейки теряются) или «заворот ломает
> трафик» (при сплите теряются сами данные). Транспортная сумма не трогается:
> `--dpi-desync-fooling=badsum` портит её намеренно. Короткие кадры (сегмент из
> одного байта при `--dpi-desync-split-pos=1`) добиваются до минимальных 60 байт.

> [!IMPORTANT]
> Вторая такая тонкость — **TSO**. Wi-Fi на Apple Silicon умеет TCP segmentation
> offload, поэтому ядро отдаёт браузерный ClientHello (1538 байт) не двумя
> сегментами, а одним суперпакетом больше MTU. pf уводит его `route-to` в `utun`,
> где TSO нет, и выбрасывает (`netstat -s -p ip` → «datagrams that can't be
> fragmented»). TCP после этого досылает **сначала хвост** (пробой потери), а
> голову — потом. Движок получает сегменты задом наперёд, сборка ClientHello
> срывается («reassemble session failed»), и голова с именем уходит в сеть без
> всякой обработки. Снаружи это выглядит как «ни одна стратегия не пробивает
> браузер, хотя curl пробивают». Поэтому, пока правила заворота активны, движок
> ставит `net.inet.tcp.tso=0` и возвращает прежнее значение при выходе
> (`MACWS_TSO=keep` — не трогать). Соединения, открытые до запуска обхода, TSO
> сохраняют — браузер после запуска стоит перезапустить.

Интерфейс выхода определяется по маршруту до реального адреса, а не по записи
`default`: VPN обычно ставит `0.0.0.0/1` + `128.0.0.0/1`, и `default` при этом
остаётся на физическом интерфейсе. Если интерфейс меняется (включили/выключили
VPN, сменилась сеть), бэкенд замечает это и переинициализируется.

> [!NOTE]
> Если поднят VPN, весь трафик и так идёт в туннель, и обход DPI для него не
> нужен: провайдер видит только шифрованный туннель. Бэкенд это замечает и
> предупреждает («packet source ... does not belong to ...»). Для нормальной
> работы zapret VPN надо выключить.

Патч к движку — [`macos/patches/macws-72.9.patch`](./patches) (≈230 строк:
бэкенд-цикл `mac_main`, инъекция вместо divert-сокета, пересчёт контрольных
сумм). Вся логика обхода взята из upstream без изменений.

### IPv6

Работает так же, как IPv4: BPF пишет кадр с ethertype `0x86DD`, MAC маршрутизатора
берётся из NDP-кэша (`ndp -an`), на utun поднимается пара адресов
`fd77:77::1`/`fd77:77::2` для next-hop в правилах `route-to ... inet6`.
(Через raw-сокет это было бы невозможно: в macOS SDK нет `IPV6_HDRINCL`.)

Заворот IPv6 включается, когда `IPV6=auto` (по умолчанию) и одновременно:

- есть маршрут в IPv6-интернет;
- `selftest` подтвердил, что инъекция и заворот v6 работают (он проверяет обе
  версии и пишет отдельные метки).

**Если IPv6 есть, но не подтверждён**, обход к нему не применяется — и тогда
dual-stack сайты (YouTube, Google, Discord) ушли бы по IPv6 мимо обхода. Чтобы
этого не было, IPv6 на обходных портах в таком случае **глушится с ответом
RST/ICMP**, и приложение сразу уходит на IPv4, который обходится. Отключить это
поведение целиком: `IPV6=0`.

`IPV6=1` — включить принудительно, `IPV6=0` — выключить. Если IPv4 и IPv6 уходят
через **разные** интерфейсы (редкий случай: v4 через VPN, v6 напрямую), инъекция
привязана к одному из них — `selftest` об этом предупредит, лечится
`MACWS_UPLINK`/`MACWS_UPLINK6` или `IPV6=0`.

### Что из-за этого не работает

- **Трафик самого root** идёт напрямую (иначе наши же пакеты уходили бы по кругу).
- Функции, которым нужны **входящие** пакеты (`--wsize`, `--wssize`,
  `--synack-split`, автохостлист `--hostlist-auto`), не работают. Ни одна из 22
  стратегий в этом репозитории их не использует, так что на них это не влияет.
- Если процесс убить `kill -9`, правила pf останутся, и трафик на нужные порты
  будет уходить в исчезнувший utun. Лечение — ниже.

## Настройки

```sh
cp macos/config.example macos/config
```

`ENGINE`, `STRATEGY_BAT` (стратегия macws), `STRATEGY` (стратегия tpws),
`GAME_FILTER=off|tcp|udp|all` и `GAME_PORTS` (аналог `Game Filter` из
`service.bat`), `IPSET_FILTER=none|loaded|any` (аналог `IPSet Filter`), порты
tpws, `BLOCK_QUIC`, `IPV6`, `USE_LISTS`, `UTUN_PEER`, `ZAPRET_TAG`.

> [!WARNING]
> `IPSET_FILTER` меняет поведение **всех** стратегий: профили с `--ipset=` не
> требуют имени хоста, поэтому срабатывают уже на SYN — раньше, чем станет виден
> SNI, — и перебивают профили по хостлистам. Значение по умолчанию `none`
> соответствует состоянию `lists/ipset-all.txt` в репозитории (заглушка), то есть
> ровно тому, как ведёт себя свежая Windows-сборка. Включайте `loaded`, только
> если цели ходят по IP без имени, и обязательно перепроверяйте стратегии. Любую переменную можно задать и через окружение:
`STRATEGY_BAT="general (ALT2).bat" sudo -E ./macos/zapret.sh start`.

Пользовательские списки подхватываются те же, что в Windows-версии:
`lists/list-general-user.txt`, `list-exclude-user.txt`, `ipset-exclude-user.txt`,
`ipset-all-user.txt` (отсутствующие просто игнорируются).

## Стратегии tpws

Нужны, только если бэкенд macws не заработал. Здесь нет fake/seqovl — из TCP-потока
их не сделать, поэтому остались `split2`, `split-sni`, `multisplit`, `disorder`,
`disorder-sni`, `oob`, `tlsrec`, `tlsrec-split`, `tlsrec-disorder`, `hostcase` и
`none` (контрольный прогон). Формат строки в
[`strategies.conf`](./strategies.conf): `имя | опции TLS | опции HTTP | описание`,
полный список опций — `macos/bin/tpws --help`. На macOS не поддерживаются `--mss`
и `--fix-seg`, и нельзя сочетать `--oob` с `--disorder`.

## VPN и обход несовместимы

Если поднят туннель, обход не нужен: провайдер видит только шифрованный канал.
Хуже того, при активном заворота мы бы перехватывали **туннельный** трафик и
отправляли его кадром в физический интерфейс, мимо туннеля — от этого сайты
перестают грузиться.

Поэтому сторож (`PF_WATCH=1`, по умолчанию включён) следит за маршрутом: как
только трафик уходит в `utun`/`ipsec`/`ppp`, он снимает правила заворота, а когда
туннель исчезает — возвращает их. Движок при этом не перезапускается. `start`
предупреждает, если туннель уже поднят.

Отдельная беда — клиенты VPN, которые перезагружают **свой** ruleset pf: они
затирают ссылку на наш anchor, и обход молча выключается. Это тот же сторож
чинит в течение `PF_WATCH_INTERVAL` секунд (по умолчанию 10). Всё, что он делает,
пишется в `/var/log/zapret.log`.

## Если pf занят другим клиентом

Сторонние клиенты (VPN и подобные) грузят **свой** главный ruleset pf командой
`pfctl -f`, и ссылка `anchor "zapret"` из `/etc/pf.conf` в активном наборе при
этом исчезает. Правила остаются лежать в анкере, но их никто не вычисляет —
заворот молча не работает, а в логе движка видно только служебный трафик.

Скрипт это обнаруживает и по умолчанию (`PF_TAKEOVER=auto`) дописывает ссылку в
активный ruleset, **сохраняя правила и анкеры остальных**. Вернуть как было:

```sh
sudo pfctl -f /etc/pf.conf
```

`PF_TAKEOVER=0` — только предупреждать. Проверить текущее состояние:
`sudo ./macos/zapret.sh status` покажет строку «активный ruleset ссылается на
anchor "zapret"». Если трафик при этом уходит в туннель VPN, скрипт pf не трогает
и предлагает сначала отключить VPN — сквозь туннель обход бессмысленен.

## Почему подбор стратегии мерит двумя пробами

`curl` отправляет ClientHello ~325 байт — он влезает в один TCP-сегмент.
Браузеры шлют ~1500 байт и больше (основной объём даёт постквантовый key_share),
такой ClientHello рвётся на два сегмента, и DPI ведёт себя с ним иначе. Поэтому
стратегия может давать 8/8 в проверке `curl` и при этом не работать в браузере.

`test-bat` меряет обе пробы: `curl` и настоящее TLS-рукопожатие с крупным
ClientHello ([`macos/src/bigch.py`](./src/bigch.py)). Рукопожатие именно настоящее:
пробник открывает TLS через OpenSSL, который сам кладёт в ClientHello постквантовый
key_share, как Chrome, — получается 1538 байт. Успех — либо рукопожатие прошло,
либо сервер ответил ошибкой TLS: и то и другое значит, что DPI соединение не резал.

Размер проверяется самой программой:

```sh
./macos/zapret.sh bigch --selfcheck            # 1538 байт, рвётся на два сегмента
./macos/zapret.sh bigch www.youtube.com        # одна проба вручную
```

Лучшая стратегия выбирается по **браузерной** пробе, но только если она вообще
блокируется на вашей сети: если нет, тест об этом прямо пишет и выбирает по `curl`.

Раньше здесь собирался ClientHello вручную, байт за байтом. Сервер отвергал такой
запрос (случайный постквантовый key_share), и проба показывала «режется» там, где
всё работало, — из-за этого несколько стратегий были признаны нерабочими зря.

## За что цепляется DPI: `why`

Когда стратегии не помогают, важно сначала понять, лечится ли цель вообще. Это и
делает `why` (в меню — пункт 16): по одной цели он проводит пять рукопожатий без
обхода и те же пять с обходом.

```sh
sudo ./macos/zapret.sh why www.youtube.com
```

| Проба | Что показывает |
|---|---|
| ClientHello 517 б, SNI есть | односегментный запрос — то, что меряет `curl` |
| ClientHello 1280 б, один сегмент, SNI есть | крупный, но всё ещё в одном сегменте: отделяет «мешает размер» от «мешает разрыв» |
| ClientHello 1538 б, два сегмента, SNI есть | то, что реально шлёт браузер |
| ClientHello 1538 б, без SNI, по IP | если эта проба проходит, блокируют по имени; если нет — по адресу |
| ClientHello 1538 б, чужой SNI, по IP | то же, но с посторонним именем — проверка, что дело именно в вашем домене |

Выводы, которые он делает:

* **большой ClientHello проходит и без обхода** — на уровне TLS хост не режется,
  причина недогрузки в другом (QUIC, сторонние домены страницы, DNS);
* **режется и без SNI, и с чужим SNI** — цепляются за адрес, а не за имя.
  Desync-стратегии тут бессильны в принципе: нужен прокси (`socks`), VPN или ECH;
* **обход лечит один сегмент, но не два** — DPI собирает TCP-сегменты, и
  расщепление его не обманывает. Тогда имеет смысл `tune` (там есть наборы с
  IP-фрагментацией, которую такой DPI часто не собирает) или ECH в браузере;
* **обход не помог даже маленькому ClientHello** — стратегия не подходит,
  нужен `test-bat` или `tune`.

`tune` перебирает 46 наборов параметров по одной цели и различает те же две пробы:

```sh
sudo ./macos/zapret.sh tune www.youtube.com
```

Наборы охватывают расщепление (`multisplit`, `multidisorder`, точки `1`, `midsld`,
`sniext+1`, во втором сегменте), фейки (`fake` с `badseq`, `badsum`, `md5sig`,
`ts`, `datanoack`, `autottl`, рандомизацией `fake-tls-mod=rnd,dupsid`),
перекрытие последовательности (`seqovl`), дубликаты (`dup`), `syndata`,
`wssize` и **IP-фрагментацию** (`ipfrag2`) — единственную ось, которая работает
на уровне IP, а не TCP, и потому иногда проходит там, где расщепление не помогает.

## Тесты проходят, а в браузере не грузится

Сначала проверьте, что сборка ClientHello в движке не срывается: `why` и `tune`
пишут это прямо («сборка ClientHello из сегментов: удачных N, сорвалось M»).
Срывы — это неполадка заворота (см. про TSO выше), а не стратегии.

Дальше два самых частых объяснения, оба переключаются из меню:

1. **QUIC.** Браузер идёт на YouTube по HTTP/3 (udp 443), а `curl` в тестах — по
   TCP. При этом QUIC-профили в `.bat` смотрят только в `list-general.txt` и
   `ipset-all.txt`, а `googlevideo.com` лежит в `list-google.txt` — значит видео
   по HTTP/3 остаётся **без обхода**, и страница открывается, но «не догружается».
   Поэтому по умолчанию `QUIC=block`: udp/443 глушится с ответом, браузер сразу
   уходит на TCP, который обходится. В режиме `QUIC=fake` скрипт дополняет
   QUIC-профиль списком `list-google.txt`, чтобы видео тоже попадало под фейки.
   После смены перезапустите обход **и браузер** (он помнит доступность h3).
2. **Ruleset pf затёрли.** Клиент VPN мог перезагрузить свой набор правил уже
   после запуска обхода. За этим следит сторож (`PF_WATCH=1`), но проверить можно
   и руками: `sudo ./macos/zapret.sh status` — там строки «активный ruleset
   ссылается на anchor "zapret"» и «сторож pf».

Если не помогло, снимите подробный лог и посмотрите, что движок делает с
соединениями браузера:

```sh
sudo ./macos/zapret.sh debug          # откройте сайт в браузере, затем Ctrl-C
grep -E "hostname:|desync profile|sending |reasm" macos/.state/debug.log | tail -40
```

Ключевое отличие браузера от curl — ClientHello у браузеров крупнее и может не
влезать в один пакет; тогда движок собирает его из нескольких (в логе это строки
про `reasm`), и смотреть надо именно на них.

## Если что-то сломалось

Обход заворачивает весь TCP/UDP на нужных портах в движок. Если движок умер, а
правила pf остались, сайты перестанут открываться. Лечение:

```sh
sudo ./macos/zapret.sh stop          # правильный способ
sudo pfctl -a zapret -F all          # аварийно: снять только правила zapret
sudo ./macos/zapret.sh uninstall     # снять всё, включая патч /etc/pf.conf
```

Для постоянной работы лучше `install`: launchd с `KeepAlive` поднимет движок
обратно и заново наложит правила. Лог — `/var/log/zapret.log`.

Все стратегии дают 0 из N:

- сначала `./macos/zapret.sh diag` — он отвечает, лечится ли это вообще:
  «рвётся только с SNI» → лечится стратегией; «TCP не устанавливается» или
  «TLS не проходит и без SNI» → блокировка по IP, и никакая стратегия zapret
  (ни на macOS, ни на Windows) тут не поможет — нужен VPN или прокси;
- `DNS не разрешается` — это подмена DNS, нужен DoH, а не стратегия;
- если у стратегии написано «заворот ломает трафик» — дело не в стратегии:
  сначала `sudo ./macos/zapret.sh selftest`, затем `debug` и смотреть лог;
- проверьте, не поднят ли VPN: сквозь туннель обход бессмысленен;
- проверки специально идут от имени обычного пользователя, а не root: трафик root
  при raw-инъекции исключён из заворота;
- контрольная цель для проверки «не ломает ли заворот трафик» выбирается **из
  хостлистов** — иначе стратегия к ней не применяется и проверка ничего не значит.

Диагностика:

```sh
sudo MACWS_SELFTEST=1 ./macos/bin/macws --debug=2     # подробно про utun/инъекцию
sudo ./macos/zapret.sh check ALT4                     # что уйдёт в pf и в движок
sudo ./macos/zapret.sh status
```

Переменные окружения бэкенда:

| Переменная | Назначение |
|---|---|
| `MACWS_UPLINK`, `MACWS_UPLINK6` | интерфейс выхода для v4/v6, если определяется неверно |
| `MACWS_INJECT` | `auto` (по умолчанию: raw-сокет, при неудаче BPF), `raw`, `bpf` |
| `MACWS_BOUND_IF` | `1` — прибить raw-сокет к uplink через `IP_BOUND_IF` (на части систем даёт `No route to host`, поэтому по умолчанию выключено) |
| `MACWS_UTUN_LOCAL`, `MACWS_UTUN_PEER`, `MACWS_UTUN_MTU` | параметры utun (IPv4) |
| `MACWS_UTUN_LOCAL6`, `MACWS_UTUN_PEER6` | адреса utun для IPv6 |
| `MACWS_MAX_PPS` | предохранитель от петли, по умолчанию 200000 пакетов/с |
| `MACWS_SELFTEST_DNS`, `MACWS_SELFTEST_DNS6` | резолверы, на которых проверяется v4/v6 |

## Обновление

```sh
./macos/zapret.sh build && sudo ./macos/zapret.sh restart
```

При смене `ZAPRET_TAG` нужен патч для новой версии: положите
`macos/patches/macws-<версия>.patch`, иначе соберётся только `tpws`.

Собранные бинарники (`macos/bin/`), исходники (`macos/.build/`), состояние
(`macos/.state/`) и `macos/config` в git не попадают.
